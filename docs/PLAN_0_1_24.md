# Plan after 0.1.23: upscaling, Oxen.ai, the builds for three platforms

Written 2026-09-22 for the sessions that build it. Read `CLAUDE.md` first. The user's word of
2026-09-22: build upscaling (item 14), Oxen.ai (item 16), the smaller Windows installer, the
Linux build, and prepare macOS as far as it goes without the Apple developer account (which
comes later this week). Qwen Image Edit 2.1 has no API yet, so item 15's API side is closed
for now. The assistant has run against a real key and works (the user, 2026-09-22), so the
checkpoint of `docs/PLAN_ASSISTANT.md` is answered by use, not by a session.

The plan is **six sessions**, each ending in a commit, a pushed hand-over paragraph in
`CLAUDE.md` and, where it says so, a release; after each one the context is cleared
(`/clear`). Every session starts by reading `CLAUDE.md` and this file's section. The rules of
every session: gates `--offline` on both backends before a commit, a mutation per new check,
`nodecopy` whenever `renderer/editor/` changes, nothing queued on the user's ComfyUI without
`/queue` empty and the user's word, the dev blog post per release (`CLAUDE.md` "Decisions").

## Session U1 - upscaling through the providers, and the whole-picture mode (release 0.1.24)

**What the user gets:** an *Upscale* button next to *Generate* and *Generate new*, and a family of
upscale recipes under *api*. Two ways to use it: **the selection** (the crop goes to the upscaler
at up to the model's factor and comes back into the selection at the document's resolution: a
detail pass, the existing run path with the result fitted by the stitch) and **the whole
picture** (the base and every layer are replaced by the upscaled picture at N times the size,
the way *Resize* does it, as one `canvas` undo step). No prompt is needed; Clarity-style models
take one as guidance.

Steps:

1. **Recipe format:** a provider recipe gets `"kind": "provider", "task": "upscale"` (the
   default task stays `edit`). An upscale variant carries `factor: { default: 2, min: 1, max: 4 }`
   (what the model offers), `fields`, `settings` rows as any variant, `limits` for the input
   size, and `prompt: false` when the model takes none. `docs/RECIPES.md` "Upscale recipes".
   Ship: `topaz_precision` (fal; *Model* row with the seven names, *Face enhancement*,
   *Sharpen*, *Denoise*, *Fix compression*), `topaz_creative`, `topaz_generative`,
   `clarity_upscaler` (fal; prompt used as guidance, *Creativity*, *Resemblance*, *Steps*),
   `seedvr2` (fal), `recraft_crisp` and `recraft_creative` (fal), and **Magnific Precision and
   Creative** (the user, 2026-09-22: "wichtig"; their own adapter `providers/magnific.js`, docs
   at https://docs.freepik.com/api-reference/image-upscaler-precision/post-image-upscaler-precision.md
   and `.../image-upscaler-creative/image-upscaler.md`: `POST /v1/ai/image-upscaler-precision`,
   header `x-magnific-api-key`, `image` as **base64** (no upload), `sharpen`, `smart_grain`,
   `ultra_detail`, an **async task** answered with `task_id` and `status: CREATED`, polled on
   its status route until the image URL is there - the ToAPIs adapter's poll loop is the
   pattern; a Magnific key row under *Settings › API providers*). Every row on its own slot
   (`recipes` gate). **Topaz on fal takes long** (minutes on a large input): the recipe
   description and the status line say so before the run ("Topaz can take several minutes; the
   window stays usable"), and the run's timeout is set to fal's queue, not the edit default.
   **Survey first, with the user's keys, in plain Node** (one session step, its findings into
   `docs/RECIPES.md`): Replicate's `collections/super-resolution` (needs the token; real-esrgan,
   clarity, seedvr2, topaz?), WaveSpeed's model list (the public route answered 410 without a
   key), ToAPIs, OpenRouter's `GET /api/v1/images/models` (any upscaler?), Comfy Cloud's partner
   nodes, Oxen's `/models` (Topaz Starlight is video; any image upscaler?). A provider that
   serves one of the shipped models gets a variant, last, no default changed.
2. **The run:** `host.runUpscale(editor, { scope: "selection" | "document", factor })`. Selection:
   `prepareCropAsync` as `runProvider` does, the request `kind: "upscale"` with `factor`, the
   answer through `finishResultAsync` (it already fits an answer of another size into the box)
   and `addResults` as a result layer; the fal adapter gets an `upscale(req, ctx)` beside
   `edit` / `generate` (one call, the endpoint from the variant's `model`, `image_url` a data
   URI, `upscale_factor` from `factor`); `providers/index.js` dispatches `kind: "upscale"` to
   `p.upscale` and refuses providers without one. Document: the base flattened? **No** - the
   *base only* goes out (layers stay layers): the answer becomes the new base at its own size,
   and every layer, mask and the selection are scaled by the same factor through
   `resizeImageNow`'s path (`inpaint_canvas.js` 3082; give it a `{ base }` argument so it takes
   the new pixels instead of resampling the old ones). A document whose base is above the
   provider's `limits.max` is refused with the size in the message (the banded whole-picture
   upscale is U3's).
3. **UI:** the *Upscale* button in the top bar (`inpaint_modal.js` `buildTopBar`), a small
   dialog (scope, factor, the recipe's own settings live in the Settings panel as always),
   the status line with the factor and the answer's size, the recipe select showing upscale
   recipes under *api* marked "(upscale)". Command `upscale` for agents and the assistant
   (`scope`, `factor`, `doc`), the policy: **asks** (costs money), `docs/COMMANDS.md`,
   `docs/MCP.md`, the tool count in `docs/ASSISTANT.md`.
4. **Gates:** `tools/upscale_test.py` against the loopback provider (a loopback `upscale` that
   returns the picture N times the size with a marker): selection mode lands a layer at the
   box, document mode resizes base, layers, masks and selection by the factor and one Ctrl+Z
   puts everything back, the refusal above `limits.max`, the command and the ask; the
   plain-Node request shape for fal's Topaz and Clarity (golden bodies in `tools/fal_test.js`
   or a new `upscale_test.js`), mutations. Both backends, `nodecopy` (the editor changed),
   the exe gates, CHANGELOG 0.1.24, the release, the dev blog post.

Checkpoint with the user before the release: one live run of `topaz_precision` on the fal key
(the user has it) on a small selection and on a 2 MP document - the first upscaler ever run
live; what fal's Topaz answers at 4x on a 4 MP input decides `limits`.

**`/clear` after U1.**

## Session U2 - upscaling on the user's ComfyUI (with U3 in 0.1.25)

1. `recipes/upscale_model_local.json`: `InpaintCanvas` -> `ImageFromBatch` (the crop only) ->
   `UpscaleModelLoader` (`model_name` as *Model*, the list from `/object_info`, which `comfy.js`
   already serves for `UpscaleModelLoader`) -> `ImageUpscaleWithModel` -> optional
   `ImageScaleBy` for a factor below the model's own -> `result_local`. Selection mode is the
   inpaint path: **the node's stitch resizes any result to the box** (`nodes.py` 761 to 763:
   `_resize_image(src, w, h)`, stretched back exactly when the aspect matches the emitted
   one), so a 4x answer lands at the document's resolution - a detail pass, never a bigger
   picture; the recipe sets `target_size: 0` so the crop goes out at its native size and
   nothing is downscaled before the model sees it (the user asked whether a bigger answer
   works at all: yes, by that resize). A
   `task: "upscale"` on a comfy recipe makes the *Upscale* button use it in selection mode and
   greys document mode out (the node's stitch has no "replace the base" - that needs the node
   to answer the raw result, a node change, not now).
2. Gate: `recipes` (slots), a `commands` step that queues nothing (the prompt built from the
   recipe checked in plain Node), `smoke` once when the user frees ComfyUI (a real model file
   from their `models/upscale_models`).

## Session U3 - upscaling in the app (ONNX), whole picture in bands

1. Model catalogue: `onnx/models.js` gets `kind: "upscale"` entries. Candidates (**verify the
   repos and the ONNX opset before wiring; none was opened**): Real-ESRGAN x4plus (Qualcomm AI
   Hub publishes ONNX exports), 4x-UltraSharp / RealESRGAN-x4 ONNX conversions on Hugging Face,
   Swin2SR (`Xenova/swin2SR-*`, transformers.js exports). Prefer a fixed 4x RGB model with
   dynamic H×W; the scale is read from the model's output shape at first run. Settings ›
   Helpers lists them like SAM2 / RMBG (download, or linked from the ComfyUI `models/` folder
   when an `.onnx` is there; `.pth` stays unusable, as the scan of 2026-09-12 says).
2. `onnx/upscale.js` (`Upscaler` beside `Matting`): tiled inference (tile 256 or 512 with a
   32 px overlap, float32 NCHW in, clamp, 8-bit out, the seams blended), on the `Runtime`
   (DML / CUDA / CoreML / CPU as the others). IPC `helpers:upscale` takes RGBA bytes + size +
   factor and answers bytes + size, in chunks for large pictures.
3. Whole picture in bands on tiles: the base read in bands (`bandPlan` / `readBand`, the row
   sources of `inpaint_bands.js`), each band upscaled in the worker with the overlap, the
   answer written into a new tile store of N times the size, then the layers scaled (step U1's
   `resizeImageNow({ base })`). This is what makes a 15k picture upscalable at all; measure the
   block per band and the whole wall on the user's 15k photo, target under 0.1 s of block per
   band.
4. Gates: `node tools/helpers_test.js` gets the upscaler on a synthetic model (an ONNX identity
   or a 2x nearest model written by the test with `onnx` protobuf, no download), `upscale_test.py`
   the in-app route on both backends, `huge_test.py` a band-mode upscale of a 4k slice.
   CHANGELOG 0.1.25 with U2, the release, the post.

## Session B3 - macOS, prepared without the developer account

Everything that can be done and checked here; signing and notarization wait for the account:

1. `package.json`: a `mac` block (`target: ["dmg", "zip"]`, `arch: ["arm64"]` - the ONNX
   binary is arm64 only, an Intel build would have no helpers; `category`
   `public.app-category.graphics-design`, `hardenedRuntime: true`,
   `entitlements: build/entitlements.mac.plist` with `allow-jit`, `allow-unsigned-executable-memory`
   (Electron needs them), `gatekeeperAssess: false`, `artifactName Scumble-${version}-${arch}.${ext}`),
   `build/icon.icns` from a 1024 px PNG (ask the user for the 1024 source of `build/icon.png`;
   electron-builder makes the icns from `icon.png` when it is at least 512, so it builds
   either way).
2. Code: `window-all-closed` keeps the app alive on darwin and `activate` recreates the window
   (`main.js` 640 to 641); a `cmdKey(e)` helper (`e.ctrlKey || e.metaKey`) at the nine
   `ctrlKey`-only sites in `inpaint_canvas.js` (and the node gets it through `nodecopy`);
   the MCP launcher's usage line and *Copy MCP registration* for
   `Scumble.app/Contents/MacOS/Scumble`; `Ctrl+Shift+A` etc. in tooltips read
   "Cmd" on darwin (`hostText` or a `modKey` string); `local.js` socket path under
   `os.tmpdir()`; `gpumem.js` answers null (it does).
3. CI: a `macos` job on `macos-latest` with `CSC_IDENTITY_AUTO_DISCOVERY=false` that builds
   the dmg and zip **unsigned** as workflow artifacts (not attached to the release: an unsigned
   mac build in the release would break `electron-updater` for nobody yet but would ship a
   download Gatekeeper blocks). When the account is there: `CSC_LINK` / `CSC_KEY_PASSWORD`
   secrets, `notarize` with `APPLE_ID` / `APPLE_APP_SPECIFIC_PASSWORD` / `APPLE_TEAM_ID`, and
   the job attaches to the draft. `docs/CODE_SIGNING_POLICY.md` gets the macOS paragraph.
4. What cannot be checked here: any gate on macOS, the CoreML provider, Retina scaling of the
   tile atlas, the app menu's *Quit* vs the single-instance lock. Written into `docs/BUGS.md`
   as "macOS: built, never run" until the user has a Mac to try it on.
