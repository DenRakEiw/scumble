==========================================================================

The spec is docs/PLAN_CORRIDORKEY.md §4.2 and §5 row I0b. The harness is tools/ck_spike/ (main.js the Electron entry,
key_process.js the utility process, ckio.js the pre-processing, sampler.ps1 the Windows counters, parity.py,

Stop A in one paragraph
-----------------------
By §4.2's list as written it is a NO-GO on Nucito's set: DirectML cannot build stage 1 at all (both ORT versions,
every optimisation level, with and without DML graph fusion), and WebGPU, which builds and runs all five graphs with
every node on the GPU, misses the parity thresholds (0 of 40 cases; the alpha channel's max error and the edge band).
Everything else on the list passes on WebGPU, most of it by a wide margin: load 7.8-9.3 s, a still at 1024 in 0.25 s
warm and 1.3 s cold after the load, the hint loop 217-220 ms end to end at 1024, 4.2 GB GPU and 5.0 GB private after a
run, everything back within 0.43 s of kill(). The parity misses need reading before Stop A decides: (1) the bf16
reference itself, run again in fp32 here, fails the same list in 14 of its 20 bucket cases, so the list measures the
reference's noise as much as ours; (2) against fp32 WebGPU's error is about 2.5x the bf16 reference's, and it comes from
WebGPU's fp16 arithmetic in stage 2 (bf16-rounded inputs change nothing; stage 2 alone on I0a's baton carries it);
(3) DirectML's own fp16 stage 2, fed I0a's baton, passes the list 8 of 8 against fp32 and is twice as fast as
WebGPU's: DirectML is the better provider if an own export (I1) gets stage 1 past DirectML; the first node DirectML
refuses is a MatMul in stage 1's decoder block dec_16.2 (section 4). By eye at 100 % the WebGPU matte of hair_green
cannot be told from the fp32 run's; inside the opaque subject 25-28 % of the pixels land below 255 and 0.3-0.7 % 5 to
15 levels below (the bf16 reference: 3-10 % and at most 0.02 %). ORT 1.29.0 (installed) and 1.30.0 give bit-identical arrays
on both GPU providers: no I0c is needed for either. The CPU provider runs the fp16 set but is no fallback (> 25 min per
768² still). The numbers Stop A asks for are in section 10.

2. The pre- and post-processing table (processing.md; inspect/)
---------------------------------------------------------------
Nucito publishes no loader (README: files and input names only; no JS loader on HF, GitHub or the web, searched
2026-11-06), so the table is read from the graphs (inputs, dtypes, shapes, the nodes that read the inputs and write
the outputs) and checked against upstream's runtime.py / video_io.py / color_utils.py / foundations.py / rvm.py:
C-RADIO takes the display RGB area-resized to H/4, MoGe area-resized to 7H/32, RVM bilinear to H/4 clamped with a zero
state; the RADIO / ImageNet normalisations and CK2's foundation_stats sit inside the graphs; stage 1 and 2 take the
asinh model code (sRGB -> linear -> asinh(x/0.008)/asinh(2000)), the hint grey / 255 white = subject or zeros with
quality -1; logits ch0 alpha raw, ch1-3 the fg code. The JS pre-processing equals numpy / OpenCV to float32 precision
on hair_green b768 (PNG byte sum 105,831,300 both; C-RADIO input sum 25,939.0450 vs 25,939.0453; MoGe 19,859.9438 vs
19,859.9446; RVM 25,943.9165 vs cv2 linear 25,943.9166; code 437,969.2999 vs 437,969.2992; hint 476,189.3256 vs
476,189.3255). I0a's bucket inputs were fed byte for byte (in/input.png, hint.png of b768_* and b1024_*). The native
cases (1408) are not a bucket of this set and were not run.

4. The node DirectML refuses (bisect_dml_stage1.jsonl)
------------------------------------------------------
Bisection over node prefixes of stage1_384x384_t1.onnx (19,170 nodes as exported; each prefix a graph of its own with
the last node's outputs as outputs, loaded on DML with fusion off in a fresh Node process, 1.29.0): prefixes up to node
17,372 build; adding node 17,373, **MatMul /s1/dec_16.2/attn/proj/MatMul** (the output projection of the attention of
stage 1's /16 decoder block dec_16.2), is refused with 80070057. dec_16.0 and dec_16.1 build. Why that MatMul
(its operand rank or shape after the window partition) is **inferred, unverified**; it is I1's lead: an own export at
opset <= 21 that keeps that projection at a rank DirectML takes.

----------------------------------------------------------------
- Cases: WebGPU 1.29 and 1.30 x 768 and 1024 x the five stills x hint / no hint (40 per version); DirectML the four
  graphs it builds (the features and stage 2 alone on I0a's baton) for hair_green and highlights_green at 768 and 1024
  (16); per case the chain (own features -> stage 1 -> stage 2) and the isolated rows (stage 1 on I0a's features, stage
  2 on I0a's baton). 1.29 and 1.30 are bit-identical: 200 of 200 WebGPU arrays and 32 of 32 DirectML arrays.
- The fp32 calibration (parity/fp32_calibration_run.json; scripts/ck_ref_fp32.py): I0a's 20 bucket cases run again

  The question it answers: how far the bf16 reference itself sits from fp32.

  <= 6.7 %, >= 0.9937; DirectML vs fp32 <= 1.4 %, >= 0.9995. Baton: WebGPU chain vs fp32 <= 2.3 %, bf16 vs fp32 <= 1.9 %.
  So WebGPU's features are as far from fp32 as the reference's.
