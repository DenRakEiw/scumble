Cause of the ~57-67 ms landing blockedMax shift between row 2 (push fit size 1000) and row 4 (push 1:1 size 1000):
  - In landSplit, the synchronous main-thread work of the landing itself (upSync + commit) is equal in both arms: on push fit
    size 1000, upSync is 4.6 -> 4.3 ms and commit is 9.7 -> 9.0 ms; on push 1:1 size 1000, upSync is 2.0 -> 2.4 ms and commit is
    15.1 -> 15.1 ms. The 57-67 ms blockedMax occurs between upSync and commit while the main thread awaits the worker pool
    (liq.orig.liquifiedAsync) and V8 runs a single deferred Major Mark-Compact GC after the 15k document setup (~255-288 MB JS
    heap).
  - In standard view order (VIEWS=["fit","1:1"]), the Map path allocates new Float64Array(ow * oh * 4) (~2.0 MB in V8 Old Large
    Object Space) on every sub-dab (~160 MB across the 80 sub-dabs of push fit size 1000), crossing V8's Old Space GC threshold
    during row 2 (push fit size 1000: blockedMax 57.4 [57.4-62.0] ms, land 76.7 [75.8-82.5] ms) so row 4 (push 1:1 size 1000) is
    GC-free (blockedMax 15.5 [15.4-18.5] ms, land 33.8 [33.6-35.6] ms). The dense path reuses _dabSrc and _dabOut (0 LO_SPACE
    allocations after the first sub-dab; heapMB0 at row 2 is 255.2 MB vs 272.2-308.4 MB), so row 2 does not trigger the major GC
    (blockedMax 11.4 [10.7-12.6] ms, land 44.9 [44.0-46.5] ms) and that deferred GC fires two rows later during row 4 (push 1:1
    size 1000, after 60 frames of 1:1 preview ImageData allocations raise heapMB0 to 288.2 MB: blockedMax 66.5 [56.5-73.0] ms,
    land 80.8 [77.0-83.5] ms).
  - Verified by running the views in swapped order (VIEWS=["1:1","fit"], ab/before/swap.json vs ab/after/swap.json): when push
    1:1 size 1000 runs as row 2, both arms hit that same major GC on push 1:1 size 1000 (before: land 83.9 ms, blockedMax 75.8
    ms, upSync 3.6 ms, commit 16.1 ms; after: land 85.0 ms, blockedMax 72.8 ms, upSync 3.6 ms, commit 15.7 ms), and neither arm
    hits it on row 4 (push fit size 1000: before land 46.4 ms, blockedMax 17.2 ms; after land 45.5 ms, blockedMax 12.3 ms). The
    block moved two rows later because the dense dab allocates ~160 MB less during push fit size 1000; it did not grow.
