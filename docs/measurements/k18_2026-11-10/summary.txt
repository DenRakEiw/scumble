K18 measurement summary (2026-11-10)
====================================

Behaviour change (`rules.md` report checklist (a)):
- Opening a TIFF no longer waits behind a running export's queued strip jobs.
- Opening another file while a TIFF is still being read now cancels the superseded TIFF's remaining worker jobs immediately instead of finishing the decode in the background.
- While a multi-band TIFF opens, the "Reading W × H px ... N %" status percentage advances by total rows decoded so far as worker bands finish rather than strictly top-to-bottom.
- When WebAssembly SIMD is unavailable, opening a TIFF now still decodes in the worker pool instead of on the window.
  (Decoded pixels on valid files and refusal messages on damaged or unsupported files are unchanged, because any band error cancels the band group, releases partial pixels, and falls back to sequential `tiff_read`.)

Note on `reader kernel/wait/decode/copy/unpredict/convert`:
- `before` (`c36840d8`) runs 1 `tiff_read` job on 1 worker (`reader jobs = 1`, `reader workers = 1`), so `reader kernel`
  is that single worker's wall time.
- `after` (`K18`) dispatches `40` parallel `tiff_band` jobs across `8` pool workers (`reader jobs = 40`, `reader workers = 8`)
  on every non-streamed variant (`own`, `lzw`, `packbits`, `raw_strips`, `noise`), and `sums()` in `tools/tiff_test.py`
  sums worker milliseconds across all 40 jobs (just as `png_part` and `tiff_part` sum across 79 jobs). Dividing summed
  `reader kernel` by 8 workers (`2,574.7 / 8 = 321.8 ms` on `own`; `4,568.1 / 8 = 571.0 ms` on `lzw`; `3,559.8 / 8 =
  445.0 ms` on `noise`) matches the wall-clock `openSteps pixels` (`482.0 ms`, `821.0 ms`, `638.0 ms`, which include
  `writeMs` `356-387 ms` on the window).
