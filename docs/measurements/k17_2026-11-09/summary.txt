K17 measurement summary (2026-11-09)
====================================

Behaviour change (`rules.md` report checklist (a)):
- When opening a tiled TIFF with uncompressed, LZW, or PackBits compression whose band fits within the non-streamed band bounds (64 MiB RGBA and 128 MiB unpacked planes), a tile that decodes to fewer bytes than its rows is now refused with `tile N holds fewer bytes than its rows` rather than `tile N holds <got> of <want> bytes`.
- When opening a multi-strip or multi-tile TIFF on the non-streamed band path, every strip or tile range in the band is now checked against the file size before decoding the band, so a later strip or tile in that band that lies past the end of the file is reported (`strip/tile M lies past the end of the file`) ahead of an earlier strip or tile that is short or damaged inside the file.
- When opening a non-streamed planar TIFF (`PlanarConfiguration = 2`) with several damaged or short strips or tiles in a band, which strip or tile is named in the refusal can differ because planes in a band are now decoded one after the other rather than advancing together.

- Untouched `openSteps stored` (`open png_part` tile-store PNG compression) moved in both directions across variants (`zlib1`: `1,263.0 -> 1,135.0` ms, `-128.0` ms; `own`: `1,200.0 -> 1,098.0` ms, `-102.0` ms; `raw`: `1,109.0 -> 1,232.0` ms, `+123.0` ms; `raw_strips`: `1,121.0 -> 1,248.0` ms, `+127.0` ms). Applying one rule across all variants:
  - On `own`, `-102.0` ms of the `-145.0` ms `openMs` median difference (`3,148.0 -> 3,003.0` ms) comes from untouched `openSteps stored`; K17's reader effect is the `-31.0` ms `openSteps pixels` win (`1,348.0 [1,335.0-1,386.0] -> 1,317.0 [1,301.0-1,326.0]` ms, `1.02x` non-overlapping, matching `tiff_read kernel` `-30.0` ms).
  - On `raw_strips`, `openMs` improved by `-99.0` ms (`3,622.0 [3,596.0-3,644.0] -> 3,523.0 [3,360.0-3,537.0]` ms, `1.03x` non-overlapping) despite `+127.0` ms in `openSteps stored`; K17's reader effect is `-245.0` ms on `openSteps pixels` (`858.0 [841.0-899.0] -> 613.0 [602.0-669.0]` ms, `1.40x` non-overlapping, `tiff_read kernel` `812.9 -> 584.1` ms, `1.39x`).
  - On `raw` (`adobe_15000x10000_raw.tif`, single 10,000-row strip, `600 MB` RGBA > `TIFF_BAND_BYTES`, `plan.streamed = true`), `+123.0` ms of `+171.0` ms in `openMs` (`3,289.0 -> 3,460.0` ms) is in `openSteps stored` and `+24.0` ms is in `openSteps base`. `raw openSteps pixels` was `+14.0` ms slower with spreads apart (`515.0 [488.0-524.0] -> 529.0 [529.0-544.0]` ms, `0.97x`), while `raw tiff_read kernel` (`482.6 [455.4-484.0] -> 494.4 [480.8-506.7]` ms) overlaps. `StripRows` is unchanged in the diff, though no separate A/A run was recorded to test whether that `+14.0` ms `pixels` gap is run-to-run variance.
- `own` and `noise` `tiff_read wait` (`868.3 [856.7-886.0] -> 935.8 [931.2-941.8]` ms and `1,361.7 [1,337.6-1,413.5] -> 1,474.2 [1,472.5-1,480.2]` ms): in `readTiffBand`, `sp.wait` sums both the contiguous `blob.slice().arrayBuffer()` read and `DecompressionStream("deflate")` `reader.read()`. Route decision (`docs/PLAN_WASM_BUILD.md` §1.1):
- Rust wins `tiffUnpack=js:rust` non-overlapping at `openMs` (and `openSteps pixels`, `tiff_read kernel`, `tiff_read decode`) on both `lzw` (`5,684.0` vs `10,541.0` ms, `1.85x`) and `packbits` (`3,416.0` vs `3,684.0` ms, `1.08x`), so `DEFAULT_ROUTES` in `renderer/editor/px/kernels.js` keeps `tiffUnpack` on `"rust"` with no override entry.
- On uncompressed multi-strip files (`compression === 1`, `raw_strips`), `J.tiffUnpack` is a single `dst.set` whereas the wasm path copies into `_in`, `memcpy`s in wasm, and copies out via `_out`: JS wins `tiff_read decode` non-overlapping (`66.6 [66.4-72.3]` vs `91.9 [89.2-98.5]` ms, `1.38x`, matching `PX_BENCH` `0.02` vs `0.05` ms while `openSteps pixels` `627.0` vs `648.0` ms and `tiff_read kernel` `593.8` vs `595.6` ms tie within spread). `kernels.js` `tiffUnpack` therefore guards `if (compression !== 1)` so uncompressed strips/tiles stay on `J.tiffUnpack` (`dst.set`).
