## The two musts

- **`canvas-core/sync-clean-before-upload-lands`** (data loss). `syncLayersOnce` sets `dirty = false` before the upload and the new `ref` after it. A Ctrl+J, or a reorder / delete / group followed by Ctrl+Z, during the autosave's upload of a large layer leaves a layer with the new pixels, the old file and `dirty: false`: after a reopen it shows the picture from before the stroke. Small fix: treat an upload in flight as dirty for copies and snapshots, or clear `dirty` only if a change counter has not moved.
- **`filters/band-filter-limit-not-over`** (wrong pixels in exports and in paid runs). A limited filter layer that is not plain (a blend mode, opacity, mask) gets `limitOver` and the missing-map rule only in `filteredCanvas`; the tiles program's `bandFilter` takes neither, so a plain export, a run's crop and frequency separation blend the band with itself where the limit is 0 (shadows darkened or lightened), while the screen is right. `limit_test.py` checks only `flattenToCanvas`. Small fix plus a test across screen / flatten / programBand.

## All confirmed findings

### must

- **`canvas-core/sync-clean-before-upload-lands`** (data-loss, small) `renderer/editor/inpaint_canvas.js:892` `syncLayersOnce`: syncLayersOnce marks a layer clean (`dirty = false`) before its upload starts, and writes the new `ref` only after the await. A copy of the layer taken during that window, by duplicateLayer or by a `layers` undo record (snapshotLayer), gets `dirty: false` together with the OLD ref and the NEW pixels. Nothing uploads that copy again, so its file is the version from before the stroke.
- **`filters/band-filter-limit-not-over`** (bug, small) `renderer/editor/inpaint_ed_filters.js:627` `filteredCanvas / filterInfo (mirrored by bandFilter)`: A filter layer's limit has two rules, and only the Canvas 2D path applies them. In filteredCanvas a non-plain layer (blend mode, opacity, mask, clip) gets `info.limitOver = true`, so the limit's weight goes into the result's alpha, and a missing depth map makes the layer draw nothing (canvas = null). filterInfo, which is shared with the tiles program's bandFilter, sets neither. In the tiles program the limit stage therefore uses mix(in, out, w), and a missing map hands the input back. programFinish then composites that band over itself in the layer's blend mode.

### should

- **`canvas-core/ask-second-question-orphans-first`** (bug, small) `renderer/editor/inpaint_canvas.js:653` `ask`: ask() sets `this.askOpen = wrap` without closing a question that is already open. The first question's backdrop stays in the DOM (inset 0, z-index 20) over the whole editor. Its finish() returns early because `this.askOpen !== wrap`, so its buttons, Escape and Enter do nothing and its promise never resolves.
- **`canvas-core/loadfile-during-setvalue-mixes-documents`** (data-loss, small) `renderer/editor/inpaint_ed_persist.js:139` `setValue`: setValue checks only its own `_loadToken` after each await, and loadFile checks only `_openToken`. A picture opened into a tab while that tab's document is still loading gets a new base (setBasePixels clears the layers), and then the restore goes on: it pushes the old document's remaining layers, selection, maps, history, saved selections and guides onto the new picture.
- **`canvas-tools/abr-block-offset-wraps-infinite-loop`** (security, small) `renderer/editor/inpaint_brushes.js:129` `blocks / sampled`: The .abr reader moves to the next block with `r.pos = (r.pos + len + 3) & ~3`, where len is an unchecked u32 from the file. The bitwise AND truncates the sum to int32, so a large len can wrap to a position at or before the current one. The `while (r.pos + 12 <= r.length)` loop then reads the same header again and never ends. sampled() (line 142, `pos = (r.pos + len + 3) & ~3`) has the same wrap.
- **`canvas-tools/bucket-fill-untracked-undo-race`** (data-loss, small) `renderer/editor/inpaint_ed_shape.js:304` `bucketFill`: bucketFill awaits floodRegion (pool composite, the coarse settle, the fine flood) and only then pushes its undo step and writes. It is not wrapped in trackEdit, so an undo pressed during the flood is not held back. It undoes the step below. The fill's push then clears the redo stack, and the undone edit is gone for good. The fill also writes into `layer`, read before the await, even when that layer has been removed meanwhile.
- **`canvas-tools/stale-text-undo-snapshot`** (bug, small) `renderer/editor/inpaint_ed_text.js:232` `buildTextControls`: The text panel's textarea and both colour inputs take a `_textUndo` snapshot on focus, and only on focus when none is held. They push it only on `change`. Nothing drops it when the field loses focus without a change, or when renderLayers rebuilds the panel under it. The next edit through the field then pushes this old snapshot. It holds the layer's text, pixels and x / y / w / h from when the field was first focused, so its undo also takes back every edit made in between.

For the last two, commitStroke pushes the step before it checks that the stroke buffer is empty.

It then draws the picture over most of it. Only the added border needs noise.
- **`canvas-select/logits-intersect-bounds-of-complement`** (bug, small) `renderer/editor/inpaint_ed_select.js:838` `SelectPart.selectLogits`: In intersect mode the band jobs (and the window loop) write the complement of the object (invert: a = 255 where the logit is <= 0), so unionBounds is the box of the complement. selectLogits then sets the exact cached bounds to old ∩ complement-bounds. - **`main-net/curl-schannel-revocation`** (bug, small) `electron/main/curlfetch.js:96` `hop`: On Windows, the curl that is used is System32\curl.exe, which uses Schannel, and Schannel's certificate revocation check is strict by default.
