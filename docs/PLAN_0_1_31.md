## How the work goes

- One package at a time; a local commit per finished step (`git -c user.name=DenRakEiw ...`, no trailer); no push and
  no release without the user's word. The main loop builds; at most one or two background agents on separate files
  (a gate against a stated API, a plain-Node test, docs). Check the 5-hour window and stop at a committed state
  around 70 to 80 %.
- Tests by risk (CLAUDE.md "Working rules"): the tiers in the table. `--offline` for every gate; the user's ComfyUI is
  a production machine.
- The editor source is `renderer/editor/`; whatever lands there goes into the node's build too
  (`python tools/build_node.py --check` must stay green: a new `host` member needs a node-side answer in the node's
  `js/host.js`, or the editor must tolerate its absence). Shell-only work (package 1) stays out of the editor.
- Each package ends with: its CHANGELOG lines under an "Unreleased" heading, the manual paragraph in `docs/MANUAL.md`,
  `lint` and `types` green, the hand-over in CLAUDE.md "Where things stand".

## 1. Canvas-only view (item 24)

**What:** Tab hides everything and the picture fills the screen; Tab or Escape returns. App-only (`renderer/shell.js`,
`renderer/shell.css`, `electron/main/main.js`, `electron/preload.js`); the editor and the node stay as they are.

**Facts from the code:**
- Tab is unhandled in the editor (`onKey` :2231-2322 and `_docKey` :1970-1993 of `inpaint_canvas.js` never look at it),
  so it falls through to the shell. `_docKey` is a capture listener on `window` registered when an editor opens; the
  shell's Ctrl+S listener (`shell.js` :2096-2109) is registered at start and therefore runs **first** in the capture
  phase. A shell Tab / Escape handler registered next to it runs before the editor's.
- The editor's Escape chain (`_docKey` :1976-1987): `pending` -> `polyPoints` -> `shapePoints` -> canvas extend ->
  `flyout` -> `textEdit` -> `compare` -> `host.onEscape` (`host.js` :725, "Nothing to cancel."). In canvas-only mode
  the shell handles Escape only when none of these is set; otherwise it lets the editor's chain run and the mode stays.
- The view is `ed.view = { scale, x, y, angle }`; `fitView()` :2409 fits and sets `_fitted = true`; the resize handler
  (:2343) refits while `_fitted !== false`, else redraws. Rulers are drawn onto the canvas (`drawRulers` :2736, flag
  `ed.showRulers`, persisted in `localStorage ipc.rulers`).
- No full-screen IPC exists; the View menu (`main.js` :577-593) has `{ role: "togglefullscreen" }` (F11) and sends
  menu commands with `send("menu", cmd)`; the preload exposes `onMenu` only (`preload.js` :216).
- DOM: `#shell-bar`, `#shell-tabs`, `#shell-main` > `#editor-host`, `<dialog id="help">`, `<dialog id="assistant">`
  (`index.html` :14-34); the editor's chrome is `.ipc-top`, `.ipc-tools`, `.ipc-side`, `.ipc-bottom`, the picture is in
  `.ipc-view`. `protect.css` :34 and `plugins/skin_90s/skin.css` :51, :90, :99 override `.ipc-view` / `.ipc-side`; the
  mode's rules go into `shell.css` under `body.shell-canvas-only` with enough specificity to win over a skin.

**Steps:**
1. **IPC** (`main.js`, `preload.js`): `window.scumble.window.setFullScreen(on)`, `isFullScreen()`, and
   `onFullScreenChange(cb)` fed from the BrowserWindow's `enter-full-screen` / `leave-full-screen`. Menu entry View >
   "Canvas Only", `accelerator: "Tab"`, `registerAccelerator: false` (a registered Tab would reach text fields; the
   label still shows the key), `click: () => send("menu", "canvas-only")`. Types: `types/globals.d.ts` if it lists
   `window.scumble` members (stage 3 is open; `any` today).
2. **Shell state** (`shell.js`): `canvasOnly(on)` exported for tests. Enter: remember `{ wasFullScreen, view: {...ed.view},
   fitted: ed._fitted, rulers: ed.showRulers }` on the shell (per document is not needed: the mode is left before a tab
   switch matters, and a tab switch leaves it). Set `body.shell-canvas-only`, `ed.showRulers = false` (without touching
   localStorage: do not go through `toggleRulers`), `setFullScreen(true)` unless already full screen, then after the
   resize (`requestAnimationFrame` is fine here: the window is visible; or wait for the ResizeObserver's refit) call
   `ed.fitView()`. Leave: remove the class, put `showRulers` back, restore `ed.view` and `_fitted` (`ed.draw()`),
   `setFullScreen(false)` only when it was not full screen before. A `leave-full-screen` from F11 or the OS while the
   mode is on ends the mode (without a second `setFullScreen(false)`). `activate()` (a tab switch) and `closeDocument`
   end the mode. The help and assistant dialogs stay open underneath but hidden by the class; nothing is closed.
3. **Keys** (a capture `keydown` listener beside the Ctrl+S one): Tab without modifiers, target not `INPUT` / `TEXTAREA`
   / `SELECT` / `[contenteditable]`, no `dialog[open]` ancestor, `!ed.askOpen`, `!e.repeat` -> toggle. Escape while the
   mode is on and nothing is pending on the editor (`pending`, `polyPoints`, `shapePoints`, `extendPending()` on the
   canvas tool, `flyout`, `textEdit`, `compare`) -> leave; `preventDefault` + `stopImmediatePropagation` in both cases.
   The menu command `canvas-only` toggles too.
4. **CSS** (`shell.css`): `body.shell-canvas-only` hides `#shell-bar`, `#shell-tabs`, `#help`, `#assistant`, `.ipc-top`,
   `.ipc-tools`, `.ipc-side`, `.ipc-bottom`; `.ipc-view` fills `#editor-host` (which fills `#shell-main`). Background
   stays the skin's canvas background. A hint `#shell-canvas-hint` ("Tab or Esc to return") at the bottom centre,
   `animation` fades it after about 3 s (`pointer-events: none`); shown on every enter.
5. **Manual and help:** a paragraph in `docs/MANUAL.md` (View), the key in the shortcut list of the help if one exists
   in `renderer/help*`; CHANGELOG line.
6. **Gate** (normal tier): a step in a small `tools/canvasonly_test.py` (or a step group in `editor_test.py`), listed
   in `run_gates.sh` as `canvasonly`: Tab -> the chrome elements have `display: none`, `.ipc-view`'s rect equals the
   window's inner size, `isFullScreen()` true; a zoomed view (`ed.view.scale = 3`) is fitted on enter and back at 3 on
   leave; Tab with focus in the prompt textarea does nothing; Escape with `ed.pending` set cancels the transform and
   the mode stays; Escape again leaves; `setFullScreen(false)` from outside ends the mode; a tab switch ends it. Run on
   the tiles backend only (no pixel path changes).

## 2. 3c History panel

**What:** the undo steps as a list with human labels, click to jump; named snapshots; a configurable depth.

**Facts from the code** (`inpaint_canvas.js`):
- `MAX_UNDO = 30` :60 and `MAX_UNDO_BYTES = 384 MB` :61 are module constants; `this.undo` / `this.redo` :1390, `historyGen`
  :1392, `undoBytes` :1407. `pushUndo(step)` :6967 -> `snapshot(step)` :6927 -> `pushUndoSnapshot(snap)` :6976 (bumps
  the gen, drops redo, trims by count and bytes). `undoStep` / `redoStep` :7279 go through `queueHistory` :7283 ->
  `historyStepNow(redo, gen)` :7320, which takes `this.snapshot(snap)` of the present onto the other stack and
  `applySnapshot`s. Entries carry `kind` (layerrect, selection, layer, layerfull, transform, mask, match, filter, text,
  layers, canvas, turn) and pixels; **no label, no time**.
- 49 `pushUndo(` sites in the editor plus `commands.js` :754, `host.js` :2191, `plugins.js` :135, `shell.js` :2168, and
  about 13 direct `pushUndoSnapshot(` sites (text edit :2861, extend / crop :3091 :3147, brush strokes :5491 :5615,
  :6719, :8252, :8387, :9514, :9708, :9782, :11027).
- `turnSnapshot()` :6886 (tiles only: `if (!this.tileMode || !this.sel) return null`) and `restoreTurn(snap)` :6918
  (pushes the present as one undo step, then applies) already are the "named snapshot" mechanism; the assistant keeps
  only the last one (`assistant_turns.js`).
- **Name clash:** `this.history` :1355 and `renderHistory()` :9794 are the *results* list (Generate tab, "History"
  section, `inpaint_modal.js` :690-702). The new panel is titled **Undo history** and its members are `undoList`,
  `renderUndoList`, `snapshots`.
- Panels: `inpaint_modal.js` `buildSidePanel` :293 builds the two panes; `section(title, open, build)` :312 and
  `ed.addSection` :321 add a `<details>` block. Undo is not persisted in `.scumble` (`docs/PLAN_DOCUMENTS.md` §3.4) and
  stays that way; snapshots neither.
- No settings key for undo; the pattern to copy is `memory.atlasMB` (`index.html` :168, `shell.js` :83, :104-110,
  :1918-1923, `electron/main/settings.js` DEFAULTS :10-39).

**Steps:**
1. **Labels.** `snapshot(step)` copies `step.label`; a table `UNDO_LABELS[kind]` gives the default ("Layer pixels",
   "Selection", "Transform", "Layer mask", "Colour match", "Filter", "Text", "Layers", "Canvas", "Assistant turn"),
   so every site shows something from the start. Then one sweep over the ~66 sites with specific labels ("Brush
   stroke", "Erase", "Fill selection", "Clear selection", "Move layer", "Flip layer", "Merge down", "Duplicate layer",
   "Remove layer", "Rename layer", "Reorder layers", "Mask from selection", "Apply mask", "Filter type", "Text edit",
   "Extend canvas", "Crop", "Smudge", "Clone", "Heal", "Gradient", "Shape", ...); the commands / plugin / assistant
   sites pass the command name or the plugin's label. `historyStepNow` gives the present-snapshot the same label as
   the step it replaces, so the list reads the same after an undo. Each entry also gets `at: Date.now()` (a tooltip).
2. **The panel.** A section "Undo history" in the Image pane, above Layers or right below it (the user judges by eye):
   rows oldest -> newest for `undo`, a marked row "Current", then `redo` rows greyed (newest first is what Photoshop
   shows; keep Photoshop's order: past above, future below). Click a past row = `undoStep()` n times, a future row =
   `redoStep()` n times, sequentially through `queueHistory` (a helper `stepTo(index)` that chains). Rendered by
   `renderUndoList()` from `pushUndoSnapshot`, `historyStepNow`, `clearUndo`; text rows only (a thumbnail per step
   would be a readback per edit and is out at 15k). A "Clear" button (`clearUndo`) with an `ask()`.
3. **Named snapshots** (tiles backend; on the canvas backend the buttons are disabled with a tooltip "Snapshots need
   the tile backend"): "Snapshot" -> `ask()` for a name -> `this.snapshots.push({ name, at, snap: turnSnapshot(), bytes
   })`; a list under the undo rows with Restore (`restoreTurn(snap)`: it is itself one undo step) and Delete
   (`releaseSnapshot`). Cap: 8 snapshots or the same byte budget as the undo stack; the oldest goes first, with a
   status line. Not saved with the document.
4. **Depth setting.** `settings.history = { steps: 30, mb: 384 }` in DEFAULTS; Settings > Memory gets two inputs
   beside the atlas budget (steps 5..500, MB 64..8192); `applyHistoryBudget()` sets `editor.maxUndo` /
   `editor.maxUndoBytes` on every editor and `newDocument` on new ones; `pushUndoSnapshot` trims by the instance
   fields (defaults = the old constants, so the node is unchanged). Note in the manual: at 15k one layer step can be
   hundreds of MB; the MB budget is the one that counts there.
5. **Commands / MCP** (`renderer/commands.js`, `docs/COMMANDS.md`, `docs/MCP.md`): `list_history` (the labels with
   index and the current position, the snapshots), `undo` / `redo` take an optional `steps`, `take_snapshot { name }`,
   `restore_snapshot { name }`. The assistant's policy: `restore_snapshot` counts as a big edit (it is undoable).
6. **Gate** (normal): steps in `editor_test.py`: three edits -> three labelled rows; click row 1 -> the state of
   after edit 1 (`get_state` / a pixel probe), redo rows present; snapshot take / restore roundtrip on tiles; a depth
   of 2 trims to 2; `list_history` over MCP in the `mcp` gate. `build_node.py --check` green (the editor reads
   `this.maxUndo ?? MAX_UNDO`).

## 3. 3e Editable layer masks in PSD

**What:** write a layer's mask as the PSD user mask channel (-2) with its record, and read one back as a mask
instead of multiplying it into alpha. Full tier: an export writer and a reader that can lose pixels.

**Facts from the code:**
- Two byte-identical writers: `PsdWriter.layer` (`inpaint_export.js` :117-142, zeros for mask and ranges at :133) and
  `PsdBandWriter.layer` (`inpaint_bands.js` :278-310, zeros at :294); both write four channels (-1, 0, 1, 2) PackBits.
  The mask is baked before that: `exportLayerStack` :8537 and `exportLayerSources` :8563 go through `layerPixels(l)`
  :2463 (a `destination-in` with `maskPx`) whenever `l.maskPx` is set.
- Reader `readPsd` (`inpaint_layered.js` :201): the mask record is parsed at :236-242 (`maskLen >= 20`), channels -2 / -3
  read at the mask rect :260-264, then `applyMask()` :184 multiplies into alpha unless `flags & 2` (disabled), note
  "N layer mask(s) applied" :334; the layer object :328 has no mask field. `loadLayered` :9192-9236 calls `addLayer`
  :9230 without `maskPx`.
- The model: `layer.maskPx` (`MaskPixels` / `TileMaskPixels`, alpha = visible, at the **layer's pixel size**, not the
  document's), `maskRef`, `maskDirty`, `maskEdit`; `maskFromSelection` :7897, `applyMask` :7933, `removeMask` :7950,
  `toggleMaskEdit` :7961. `.scumble` stores `maskRef` separately (:12114, :12151). ORA has no mask support in either
  direction (`readOra` :372).
- Fixtures: `tools/layered_test.js` already builds PSDs with -2 masks (:88-117, :190, :284).

**Steps:**
1. **A mask-off flag** (`layer.maskOff`, default false): the compositor and `layerPixels` treat the mask as absent when
   set; the row UI gets the toggle (Shift+click on the mask badge, like Photoshop). Needed for the PSD flag both ways
   (package 6's "disable" is this and is then done). Persisted in `.scumble` and the autosave bundle (a new optional
   field; the reader defaults it).
2. **Write.** The layer source for PSD carries the raw pixels (no bake) plus a mask source when `l.maskPx` exists:
   both go through the same geometry as the pixels (a scaled layer resamples its mask the same way; today the pixels'
   path decides how). Record: channel count 5, channel -2 with the mask bytes PackBits like the others; layer mask data
   length 20: rect = the layer rect (4 x i32), default colour 255, flags = `maskOff ? 2 : 0`, 2 bytes padding. Both
   writers; the pool path (`tiff_part`-style op) reads mask rows from `TileMaskPixels` in bands. ORA keeps baking
   (unchanged, noted in the docs).
3. **Read.** `readPsd` returns `mask: { data, rect, defaultColor, disabled }` instead of applying it: the -2 channel
   placed into a layer-sized 8-bit map (outside the mask rect = default colour); a -3 (vector mask raster) too when no
   -2 exists. `loadLayered` builds `maskPx` from it (`MaskPixels` at the layer's pixel size), sets `maskOff` from
   `disabled`; the note becomes "N layer mask(s) kept as masks". `applyMask` stays for the `.ora`-less callers if any.
4. **Round trip of `.scumble` and PSD:** a mask written by us reads back byte for byte at the same geometry; a mask on a
   scaled layer reads back at the export geometry (documented, not exact).
5. **Tests** (full tier): `tools/layered_test.js` extended (write with mask -> read -> bytes equal; a disabled mask;
   a mask smaller than the layer from a hand-built fixture; a layer without mask writes four channels as before);
   gate `layered` on both backends; `docperf`-style measurement at 15000 x 10000 with a mask (one channel more per
   layer: the time and the file size); a mutation round of the writer and reader (about 8 mutations: flags, rect,
   default colour, channel count, PackBits length, the placement). A file opened in GIMP by the user (free; Photoshop
   / Affinity if available) — by eye, not a gate.

## 4. Brushes (PLAN_0_1_29 §4)

Order inside the package; each step is its own commit and gate step.

1. **Measure first** (0.5 d): smudge, clone and heal at 15k on the tiles backend (`perf`-style rows through a small
   script: ms per move at 50, 200 and 400 px). `smudge` draws from the whole-layer mirror; clone / heal call
   `sampleCanvas(o.sample)` / `compositeCanvas()` at the press (`inpaint_canvas.js` :3285-3313) - the whole picture.
2. **Regional sources** (2 - 3 d): the dab reads its box from the tiles (`readBox` of the layer, and a composite box
   for "all layers" through `bandPlan` / `readBox` of the stack); clone and heal sample a box around the source point
   that follows the offset; no `baseCopyLayer()` on the base for smudge (a result layer or a paint layer instead, the
   user's choice in the options bar). Re-measure; the numbers go into `docs/PERFORMANCE.md`.
3. **Pro smudge** (3 - 4 d, full tier for the kernel): a carry-buffer engine as a Rust kernel in `crates/px`
   (`smudge_dab`: carry RGBA, strength, length / rate, alpha handling) with its bit-exact JS twin and a plain-Node test;
   sample *layer / current and below / all layers*; finger painting (the paint colour seeds the carry); pressure ->
   strength; tips and spacing from the brush library (`host.brushLibrary`, `docs/BRUSHES.md`).
4. **Clone** (1 - 1.5 d): a source overlay (the source region ghosted under the cursor), rotate / scale / flip of the
   source in the options bar, tips.
5. **Flow, pressure curves, stabiliser** (1.5 - 2 d): flow as build-up within one stroke (the `StrokeBuffer` gets a
   per-stroke accumulation at flow < 1), coalesced pen events (`getCoalescedEvents`), a pressure curve select
   (linear / soft / hard), a stabiliser slider (a pull-string of N samples). Gate steps with synthetic pointer events.
6. **Blur and sharpen brushes** (0.5 - 1 d, from the competitor's Blur / Sharpen / Smudge flyout): the same regional
   dab path with a box blur / unsharp kernel; cheap once step 2 exists.
7. **The 400 px size cap** (0.5 d): measure the dab cost at 1000 and 2000 px on the regional path, raise the cap to
   what stays under ~30 ms per dab at 15k, or make it a share of the document's short side.
8. **Frequency separation** (1.5 - 2 d, full tier: a blend mode): the action (a blurred low layer, a high layer in
   linear light) and the **linear light** blend mode in every path (GL compositor, Rust `composite_tile` with an ABI
   bump and the JS twin, the Canvas 2D emulation, PSD / ORA blend maps both ways, the reader). Measured against exact
   floats (the three-rounding trap in CLAUDE.md).
9. **Dodge and burn** (1.5 - 2 d): the one-click layer (50 % grey, soft light) as an action; dodge / burn / sponge
   brushes on the regional path (shadows / midtones / highlights range, exposure).
10. **A brush panel** (1 - 1.5 d, optional, from the competitor's Brushes panel): a section with tip thumbnails, a
    stroke preview, recent tips and a search over the library, beside the Tip select of the options bar. Looks only:
    light tier.

## 5. Repair, remove, liquify (PLAN_0_1_29 §5)

1. **The Poisson solver** (3 - 4 d, full tier): `crates/px` `poisson_blend` over a box (a multigrid or a bounded
   Gauss-Seidel on the stroke's box, guide = the source patch's gradients, boundary = the destination), the bit-exact JS
   twin, plain-Node tests against a float reference; run in a pool worker per stroke. Measure a 512² and a 2048² box.
2. **Healing brush on the solver** (1.5 - 2 d): the plain heal of today paints the preview, the solver runs at release
   over the stroke's box and replaces it (the live-stroke gate gets an explicit "healing" step: preview differs from
   commit here, by design).
3. **Remove / spot heal with LaMa** (3 - 4 d): Big-LaMa's ONNX port beside SAM2 and BiRefNet in `electron/main/onnx/`
   (`lama.js`; 512 x 512 input, the crop / scale / stitch through `stitch.js`); a *Remove* tool (brush a region, run on
   release) and a provider variant `inapp.lama` so *Generate* with that recipe fills the selection offline. **Before
   the code:** the licence of the ONNX port confirmed (Apache-2.0 expected; MI-GAN is out), and the user's answer on
   shipping vs download (download like SAM2 proposed, `docs/HELPERS.md`).
4. **Patch tool and content-aware move** (2 - 3 d) on the solver: a lasso region dragged to a source (patch) or a
   region moved with its hole filled (move: LaMa for the hole, the solver for the seam).
5. **Liquify** (4 - 6 d, full tier for the bake): push / grow / shrink / swirl / restore, a freeze mask; a displacement
   field over the touched region only (the design of `docs/PLAN_0_1_7.md` §4 predates the tile engine), a GL preview
   of the field, the bake in bands through the pool; the base needs a copy or a result layer as the target.

## 6. Layers pro (PLAN_0_1_29 §6)

1. **Multi-selection** (2 d): Shift / Ctrl click in the layer list, `ed.selectedLayerIds`; move and transform together
   (one `pending` over the union box), merge selected, delete selected, visibility / lock for all selected. Commands:
   `set_active_layer` takes a list.
2. **Align and distribute** (0.5 - 1 d): to the canvas or to the selection box; an options-bar row of the move tool.
3. **Clipping** (2 - 3 d, full tier): a layer clipped to the one below (`layer.clip = true`); "a filter on this layer
   only" is `mix(in, filtered, baseAlpha)`, the post-stage item 22's *Limit by depth* will reuse; GL, Rust
   `composite_tile` (ABI, JS twin), `stackPlan` / program, Canvas 2D; the PSD clipping flag both ways; the row UI
   (Alt+click on the boundary like Photoshop); the node build.
4. **Mask operations** (0.5 - 1 d): invert, reveal all / hide all, disable (built in 3e), a `set_mask` command over MCP
   (`{ layer, op: invert | reveal | hide | enable | disable | remove | from_selection }`).
5. **Groups as folders** (3 - 5 d, full tier: the compositor walks them): visibility, collapse, lock, move together,
   PSD `lsct` both ways, `.scumble` and the autosave bundle (a `children` field), the layer list as a tree. Isolated
   groups with their own opacity and blend (a nested composite in every path, 7 - 9 d more) only on the user's word.
6. **Fill layers** (1 d): colour and gradient as a reach-0 filter type (they exist as filter kinds if it fits the
   filter-layer model; otherwise a paint layer filled by an action).
