- **Array allocation in `snapRgb` (`renderer/editor/inpaint_edges.js:55`)**:
  `snapRgb` returns a fresh 3-element `[r, g, b]` array on every invocation. In `snapField`, the 4x4 bilateral kernel calls `snapRgb` 16 times per sample point (16 array allocations per point). For interactive point queries (hover or `sample_depth`) this is unnoticeable, but if `snapField` is ever used in a CPU fallback loop across full images, inlining or reading directly from the `Uint8Array` guide data will eliminate millions of allocations.
- **Overlap window ramp with dropped neighbors in `fuseTiles` (`renderer/editor/inpaint_edges.js:456-477`)**:
  `oxLeft, oxRight, oyTop, oyBot` are computed by inspecting all tile boxes without checking whether adjacent tiles were dropped (`dropped === true`). In the interior of a surviving tile adjacent to a dropped tile, `sumWHi / sumW` normalizes to `Hi` as expected, but right at the boundary where `sumW` drops below `1e-6`, the high-frequency contribution steps to 0. When R2-S7 implements the full detail pass, it may be beneficial to smoothly feather `Hi` towards 0 at transitions into dropped tiles.
- **JSDoc type signature for `map` in `snapField` (`renderer/editor/inpaint_edges.js:62`)**:
  JSDoc declares `@param {{ data: Uint16Array, w: number, h: number } | Uint16Array} map`. However, line 77 reads `map.w` and `map.h` directly (`const mw = map.w, mh = map.h;`), which would yield `undefined` if a bare `Uint16Array` were passed. All current callers pass `{ data, w, h }` matching the module convention, but the JSDoc type should strictly reflect `{ data: Uint16Array, w: number, h: number }`.
