## S1: the status kind (item 45, the mechanism)

**What exists.** `InpaintEditor.setStatus(text)` (`inpaint_canvas.js` near 3363) writes `this.status`, the app's
status span `statusEl` (`inpaint_modal.js` near 50, a `span` without a class in `div.ipc-bottom`) and the node
thumbnail's `nodeStatus` (`div.ipc-status`, near 2214). `host.hookStatus` (`host.js` near 646) wraps it with one
argument, sets the title, and logs a line that matches
`/^(error|failed|could not|cannot|no api key)|error invoking|failed[:.]| failed /i` as an error. The token
`--sc-error` exists (`inpaint_theme.js:23`, `docs/SKINS.md`); the 90s and duck skins set it. Nothing in `renderer/`
handles `prefers-reduced-motion`. `this.status` is read as a string in 418 places in 50 test files and in
`commands.js` (`failed()` near 1508 decides `generate`'s failure from the text): it stays a string.

**Build.**
- `setStatus(text, opts)`: `opts` a kind string or `{ kind }`; kinds `"error"`, `"warn"` (looks the same: the user
  counts warnings as errors; the log gets level warn) and `"info"` (forces a plain line). Without a kind the text
  decides (`statusKindOf`): the regex above, plus the "... needs X: download it in Settings" lines. The kind lands
  in `this.statusKind` (`""` for a plain line).
- The classes `ipc-status-error` (the colour `var(--sc-error)`) and `ipc-status-blink` (five pulses, then the
  steady colour) on `statusEl` and `nodeStatus`; every error line restarts the blink; the next plain line drops
  both. `@media (prefers-reduced-motion: reduce)`: no animation, steady red. `statusEl` gets the class
  `ipc-statusline`.
- `hookStatus` passes `opts` on and logs by `statusKind` (error / warn) instead of its own regex.
- `set_status` (MCP) takes an optional `kind`; `docs/COMMANDS.md` regenerated.
- The 90s skin: a red glow instead of the green one on an error line.

**Traps.** `hookStatus` dropped a second argument; a line appended to the current one (`${ed.status} ...`, `host.js`
near 1827, 3500, 3541, 4117, 4414) is a new call and takes its own kind; `skins_test.js` wants every `var(--sc-*)` in
`STYLE` with a fallback; no new `host.*` member (the node's host would need it, `build_node.py --check`); no word
`host.something` in an editor comment (0.1.47's trap).

**Test.** A `log` gate step: an error line has both classes, one running animation with five iterations and the
`--sc-error` colour; a second error restarts it; a plain line clears it; an explicit kind beats the text; the
download line counts; `set_status` with a kind; the log levels; under emulated reduced motion no animation and still
red. `skins`, `lint`, `types`, `commands` (the description).

**S1 as built (2026-10-13).** As above, with three changes from a review workflow (13 agents, each finding checked
by a second one): the blink class goes at `animationend`, or a hidden tab shown again (`display: none` and back)
would blink its old line anew; the same line again while it still blinks keeps the blink (the object tool asks for
SAM2 on every pointer move, and now writes its line once); `failed[:.]` in the text test needs a space or the end
after it (`shot_failed.png` in a success line), and the three *Saved ...* lines of the exports pass `"info"`. The
`log` gate's steps `status_kinds` and `status_reduced_motion`; a mutation of the `animationend` fix turns the first
one red. Seen live in a dev instance (the user's download line, red after the blink).

## S3: the progress bar in the status row

**What exists.** ComfyUI's websocket messages reach the renderer unfiltered (`comfy.js` near 210, `main.js` near
113, `host.js` near 4701 `api.dispatch`). **The app already shows a bar**: `shell.js` near 2227-2257 fills the title
row's `#shell-progress` from `progress` events (any prompt of this client, helpers included, per node, hidden 800 ms
after the end) and ticks `label · N s (+k)` for API runs; `generate_test.py` (near 828, 859, 1287) reads it. Nobody
listens to `executing`, `execution_start`, `execution_cached` or `progress_state`. A local Generate frees its button
after queueing (`inpaint_canvas.js` near 23909) and gives no other feedback in the editor; in the node the editor is a
full-window overlay over ComfyUI's own progress (the issue's point). `host.queueGenerate` sets `lastPromptId` (near
3540) and `_localRuns` (near 3552) after the POST answers; API runs carry a token `{label, started, editor, runId}`
(`runProvider` near 1746); `provider:edit` sends no progress, Comfy Cloud polls a status only.

**Build.** A module `renderer/editor/inpaint_progress.js` (`RunProgress`; add it to `FILES` in `build_node.py`):
`track(promptId, nodeCount)`, `event(type, detail)`, `timer({label, started} | null)`, `clear()`. `execution_start`
"Starting", `execution_cached` lowers the node count, `executing` node k of n (top-level ids:
`String(display_node || node).split(".")[0]`), `progress` value / max of that node, never backwards per node, a second
stepped node restarts the bar ("pass 2"); reset on success, error, interrupt, `executing` with `node: null`,
`queue_remaining: 0`, a disconnect, the editor's close. A `span.ipc-run` (a 96 x 4 px track and a short label) between
`statusEl` and `.ipc-kbd` (`inpaint_modal.js` near 50), so `setStatus` never wipes it; `statusEl` gets
`min-width: 0; overflow: hidden; text-overflow: ellipsis`. App host: `track` after the POST answers (3552, 2555), the
seven event types forwarded through a lookup that also knows `_localRuns`, `timer()` from `notifyProviderRuns` (near
2490). Events that arrive before the POST's answer are held a few seconds. No width transition under reduced motion.

**Node** (later, its own files, not built in 0.1.48): the node's `api.queuePrompt` wrapper (`inpaint_node.js` near
161) would call `track`; its host returns no prompt id today.

**The user's answer (2026-10-13):** both bars stay; the title row's keeps every tab's runs and its Cancel.

**Seen, not run** (to `docs/BUGS.md`): with two local runs queued, `lastPromptId` names only the second; the first

**Test.** A `generate` gate step that dispatches synthetic events (as near 352-422): the fill, the label, the reset;

**S3 as built (2026-10-13).** As above: `renderer/editor/inpaint_progress.js` (`RunProgress`, no DOM; `build_node.py`

## S5: the size checks

**What exists.** The document ceiling (`checkBaseSize` near 18069: 65,535 px a side and 1,073,741,824 px, tiles only)
is not what limits these paths: a whole-picture landing (`host.js` `landWholePicture` near 2016), `resizeImageNow`
(near 5817) and `extendCanvasNow` (near 13580) make single canvases with the editor's **unchecked** `makeCanvas` (near
783), so their real ceiling is 65,535 px a side and 268,435,456 px on both backends. The upscale checks before a run
(`upscaleSizeRefusal` / `upscaleOutRefusal`, `host.js` near 1867-1892) know the recipe's `limits` only. Over it today:
Magnific Precision (2..16; 4096 x 16 = 65,536 px), Magnific Creative on Comfy Cloud (8, 16), SeedVR2 (up to 8),
Topaz Generative on Oxen (up to 6). The Resize panel's `max=16384` is an attribute (typed values pass); MCP
`resize_image` refuses above the canvas limit (`commands.js` near 2190, its wording tested at `commands_test.py`
1651); `extend_canvas` checks nothing and crops before it extends. `MANUAL.md` near 347 promises a gigapixel and a
refusal "before it costs you anything": neither is true.

**Build.** `renderer/editor/sizelimit.js` (no imports; `FILES` in `build_node.py`): `CANVAS_MAX_SIDE`,
`CANVAS_MAX_PIXELS` (`inpaint_tiles.js` re-exports them), `canvasSizeRefusal(w, h, what)`, `largestFactor(w, h,
spec)`. Guards: `upscaleOutRefusal` for the whole picture (names the size and the largest factor that fits; the
dialog passes `{limits, factor, name}` at `shell.js` near 1807), `landWholePicture` before it makes the canvas
(routes where the model picks the factor), `resizeImageNow`, `extendCanvasNow` and `applyFrame` (the intermediate
size before either step), `extend_canvas` up front. `MANUAL.md` corrected.

**Say the behaviour first** (memory `scumble-say-behaviour-first`): an answer that arrives too large after it was
paid for is refused ("nothing was changed") rather than scaled down; ask the user before building.

**Test.** `tools/sizelimit_test.js` (plain Node: the edges and `largestFactor`); an `upscale` gate step with a
loopback recipe `factor {min: 1, max: 16}` on 4096 x 2304: 8x refused with the text and the provider never called,
5x goes; `editor` steps for Resize, the frame and `extend_canvas`.
